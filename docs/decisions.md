# Decision log

These decisions came out of a structured "grill" session before any code was written. An AI agent interviewed the developer one question at a time, offered options with trade-offs, and the developer made each call. The scope summary is in [requirements.md](requirements.md).

| # | Decision | Alternatives considered | Reasoning |
|---|---|---|---|
| 1 | v1 is primarily a **data-entry tool**, with three insights: median salary, total payroll and top-paid employee, each **by country** | Full analytics dashboard | The HR manager's daily pain is maintaining data in Excel. The insights answer the most common questions without building a BI tool. |
| 2 | Pay comparisons and gap analysis are **deferred** | Include in v1 | Doing them properly needs role and level normalisation. It's better done well later than badly now. |
| 3 | **All salaries are stored in USD** | Local currency only; local currency + static rates; live FX | Simplicity. Global totals work without a rates table. |
| 4 | **Current salary only**, no history | Salary history table with effective dates | v1 metrics don't need history. It pairs naturally with an audit log later. |
| 5 | Employee fields: employee code, full name, email (unique), gender, job title, department, level, country, hire date, salary | Status column | Termination is represented by `deleted_at`, so a status column would duplicate it. |
| 6 | **Termination is a soft delete** (`deleted_at` = termination date) and is **irreversible**. Terminated records are read-only. | Reinstate action; hard delete | Keeps history for reporting while keeping `deleted_at` a trustworthy date. |
| 7 | Soft delete via **paranoia** | `discard`; hand-rolled | Developer preference and familiarity. paranoia's `destroy` stamps `Time.current`, so a `TerminateEmployee` service sets `deleted_at` explicitly to support a custom termination date. `restore` is never exposed. paranoia is in maintenance mode, which is acceptable for this scope. |
| 8 | **Auth: devise + devise-jwt**, multiple users, **no signup**, users created by the seed script, **all users equal** | Open signup; invite flow; roles | A public URL holding salary data must not allow self-registration. There's only one persona, so roles add nothing yet. |
| 9 | CSV/Excel **import deferred to v2**. The seed script is the v1 data path. **CSV export is in v1.** | Import in v1 | Import is a feature in its own right (validation, error reports, duplicates). Export is cheap and immediately useful. |
| 10 | Country, department, level and gender are **fixed lists as string-backed Rails enums** | Lookup tables with admin UI; free text | Guarantees clean grouping for per-country metrics. Readable values in the DB and in CSV exports. |
| 11 | Seed data: **level base × country multiplier × ±15% noise**, uneven country headcount, level pyramid, **fixed random seed**. Names come from Faker, drawn from the same seeded random | Uniform random salaries; a hand-written name list | Makes the per-country metrics meaningful in the demo. A fixed seed makes it reproducible (for a given Faker version, pinned by the lockfile). A ~75-name hand-written list repeated the same full names across 10k employees. |
| 12 | Employee list: search (name, email, code), filters (country, department, level), sort, **server-side pagination**, Active and Terminated views, **filters in the URL**, edit in a **drawer** | Client-side pagination; separate edit page | 10k rows shouldn't be loaded into the browser. A drawer keeps the HR manager's place in the filtered list. |
| 13 | **Backend first**, frontend afterwards | Build both in parallel | One layer at a time keeps AI-assisted changes small and reviewable. |
| 14 | **RSpec + FactoryBot + shoulda-matchers** | Minitest | More common in Rails teams, with readable request specs. |
| 15 | **Kaminari** for pagination | Pagy | Developer familiarity. |
| 16 | **Alba** for serialization | Plain Ruby serializers; jbuilder; `as_json` | Declarative and well maintained. Handles collections, and camelCase keys for the React frontend are a one-line option. |
| 17 | Salary is stored as **whole-dollar integer** | Decimal; integer cents | Annual salaries are set in whole dollars. An integer avoids float errors and keeps the API simple. |
| 18 | Frontend is **plain JavaScript** | TypeScript | Keeps the existing Vite scaffold and avoids setup cost. API shapes are documented instead of typed. |
| 19 | **Mantine** for UI components | MUI; Tailwind + headless primitives; plain CSS | Ships Drawer, Table, Select, DateInput, notifications and form hooks, which cover almost every screen. |
| 20 | **TanStack Query** with a thin fetch wrapper for server state | `useEffect` + fetch; SWR | Handles stale responses, keeping the previous page visible while the next loads, and refreshing the list after writes. Simple to learn for someone who knows `useEffect`. |
| 21 | **React Router v7**, with filters, sort and page as `useSearchParams` | TanStack Router; hand-rolled history API | The URL is the single source of truth, so views can be bookmarked and shared. |
| 22 | JWT stored in **localStorage**. Any 401 clears it and redirects to login. | sessionStorage; memory only | The HR manager stays logged in across browser restarts. Trade-off: the token persists on a shared machine until it expires, and is exposed to XSS. |
| 23 | **Vitest + React Testing Library**, mocking our `api` module. About 5-8 tests on critical flows only. | MSW; no tests; Playwright e2e | Light, fast and deterministic. Keeps the "every slice ends with passing tests" rule without heavy setup. |
| 24 | The terminate dialog **always records today** as the termination date, with no date picker. The API's optional `terminated_on` stays. | Editable date in the UI (the original requirement) | Your call, made while reviewing the screen designs: a simpler dialog for v1. Backdating can be added to the UI later with no backend change. |
| 25 | The 12 v1 screens are designed and exported to [frontend/design/v1-screens.pdf](../frontend/design/v1-screens.pdf). The build follows them, except where the backend or a decision overrides: dropdown options come from `/meta`; the employee code is assigned by the server (hidden on Add, read-only on Edit); the email-taken error is the server's generic message; the header shows the signed-in email and its initials; tab counts come from `meta.total_count`; there is no "Quick raise"; the Terminated list has no "Terminated in" filter (the API doesn't support one); Gender sits on its own row, since four options don't fit beside Salary; Add, Edit and the terminated View open in a **centered modal**, which supersedes the side drawer in #12. | Build the mockup literally; side drawer (#12) | The mockup used placeholder values and a few things the API can't supply. The modal was chosen in the designs. |
| 26 | Insights: the top earner's subtitle is their **level**, not their job title, and their name **opens the Edit modal**. Large totals are **compact** ("$653.1M") with the exact figure on hover. Countries are listed by headcount. | Add `job_title` to the insights query; link to a name search; plain text; exact totals | Level needs no backend change and is what drives pay here. Opening Edit reuses `GET /employees/:id` and the existing modal. Nine-digit totals are hard to scan, and the exact value is one hover away. |
| 27 | CSV import is **create-only**. Every row adds a new employee and the server assigns its code. An email already in use (including by a terminated employee) or repeated in the file is a row error. | Upsert by `employee_code`; upsert by email | It fits the migration-from-Excel use case and keeps codes server-assigned (#25). Upserts would allow bulk salary changes with no history or audit log (deferred, #4), and an email-keyed upsert turns a typo into a duplicate person. |
| 28 | Import is **all or nothing**. Every row is validated first. If any fails, nothing is written and every error is listed by spreadsheet row number and field. | Import the valid rows and report the rest | There's no half-imported state to reason about. The HR manager fixes the file and uploads it again. |
| 29 | Added the **csv** gem for parsing imports | Hand-roll a parser, as the export does | csv is Ruby's standard CSV library, a bundled rather than default gem since Ruby 3.4. Reading quoted fields and embedded line breaks correctly is much harder than writing them. |
| 30 | The import runs as a **background job** and records its outcome on an `employee_imports` row, which the frontend polls. Problems with the whole file (size, encoding, CSV syntax, columns, row count) are still rejected in the upload request with a 422. The uploaded CSV is kept on the row until the job finishes, then cleared. | Synchronous request with a row cap (measured at about 3.5s for 10k rows) | Your call: it keeps requests short and copes with larger files. Checking the whole file up front means the commonest mistake, uploading the wrong file, still gets an instant answer. Clearing the upload avoids keeping a second copy of salary data. |
| 31 | Import formats: the export's column names, matched loosely; fixed lists accept the value or the label, in any case; dates **only as `YYYY-MM-DD`**; whole-dollar salaries; at most 10,000 rows and 5 MB, UTF-8 | Accept local date formats; read `.xlsx` directly | `03/04/2026` is a different day in the US and the UK, so guessing could silently store wrong dates. Excel saves "CSV UTF-8" directly, so reading `.xlsx` (another gem) isn't needed yet. |
| 32 | Import UI: an **Import CSV** button on the Active list opens a centered modal that goes from choosing a file, to importing (polling every second), to the result. Row errors are listed as Row and Problem in words ("Hire date must be a date in YYYY-MM-DD format"), showing the first 100 rows. A header-only **template** can be downloaded. The modal can always be closed; closing stops the polling, but the import still finishes on the server. | A separate import page; a drag-and-drop zone (`@mantine/dropzone`, a new dependency); blocking close while importing | It follows the modal pattern (#25) with no new dependency. The template saves guessing column names. Never trapping the user matters because the job may not run (a dev server restart, or a worker missing in production). |
